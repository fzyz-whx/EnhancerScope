# 我用 0.5% 的参数微调了一个基因组语言模型，然后把它塞进了浏览器

> 技术博客稿 · 项目：[EnhancerScope](https://github.com/fzyz-whx/EnhancerScope) ·
> 在线演示：https://fzyz-whx.github.io/EnhancerScope/
> 写作说明：本机网络无法访问知乎/博客园等平台，稿件入库待发布；内容与仓库中的文档一致。

## 一、我想验证的一件事

基因组语言模型（DNABERT-2、HyenaDNA 这类）在论文里通常以"预训练 + 下游微调"的范式出现。
但我真正好奇的是一个更具体的问题：

> **在一张 8GB 显存的笔记本显卡上，只微调 0.5% 的参数，能不能打赢一个从零训练的全量 CNN？**

如果能，那"预训练值钱"这句话就有了直接证据；如果不能，我也想知道差在哪。
于是有了这个项目：在果蝇 S2 细胞的 STARR-seq 增强子活性数据上，把
k-mer+GBDT、CNN、语言模型零样本、LoRA 微调四条路线放进同一张表里对比。

## 二、防泄漏不是口号，是几行断言

增强子序列里有大量同源重复。如果按常规随机划分，近似重复的序列会同时落进训练集和测试集，
指标会虚高——这是这类任务最常见的坑。所以划分必须在**染色体级别**做：

- train：11 条染色体臂（402,278 条）
- valid：chr2R 左半（40,570 条）
- test：chr2R 右半（41,186 条）

听起来简单，但"我以为我划分对了"和"我能证明划分对了"是两回事。我把它们变成了断言：

```python
# scripts/verify_split.py（CI 可跑）
assert 三个 split 的 id 零交集
assert train 与 valid/test 的染色体零重叠
assert 每一条序列长度都是 249bp 且只含 ACGT
# 另外用 numpy 前缀最大值法精确计算区间重叠：valid vs test = 0.0%
```

再配一份 sha256 校验清单，防止数据在流水线里悄悄漂移。
**这套断言后来在面试准备时成了最有用的一段代码**：它把"我很严谨"变成了一句可执行的话。

## 三、负结果比正结果更费脑子

四条路线跑完，数字是这样的（test 集 Spearman ρ）：

| 方法 | Dev | Hk |
|---|---|---|
| k-mer(6)+GC → LightGBM | 0.581 | 0.519 |
| DeepSTARR 风格 CNN（从零训练） | **0.639** | 0.566 |
| DNABERT-2 零样本（embedding + Ridge） | 0.428 | 0.363 |
| **LoRA 微调 DNABERT-2（0.50% 参数）** | 0.6214 | **0.5722** |
| LoRA 微调 HyenaDNA（3.3M） | 0.2845 | 0.2486 |

两个结论：微调把 DNABERT-2 从 0.428/0.363 拉到了 0.6214/0.5722（+0.19/+0.21），
并且只调 0.5% 参数就在 Hk 上超过了全量从零训练的 CNN。

但真正让我花时间的是最后一行：**HyenaDNA 微调完全失败**，甚至低于 k-mer baseline。
训练 loss 从 2.46 只降到 2.42——它几乎没学动。

我没有把它从表里删掉。我给的是一组**可检验的假设**：参数容量差 35 倍；
单碱基分词让序列从 63 个 token 变成 249 个；超参是为 DNABERT-2 调的（LoRA 只调了 98k 参数）；
target_modules 选在 Hyena 算子的 in_proj/out_proj 上、未做消融。
在面试里，"我失败了，这是我的四个假设和验证计划"比"我全都成功了"更可信。

## 四、ONNX 导出：我给自己设了一道闸门

把模型搬进浏览器要过 ONNX。但"导出成功"不等于"导出正确"，所以我加了一道**数值一致性闸门**：
导出后用 96 条真实 test 序列对比 PyTorch 与 onnxruntime 的输出。

- LoRA DNABERT-2（fp32，481MB）：max|Δ| = 7e-6，Pearson 1.0
- CNN（0.81MB）：max|Δ| = 9.5e-7，Pearson 1.0

闸门不通过，脚本返回非 0，不允许发布。这道闸门后来救了我一次：我一度怀疑模型被量化坏了，
是它告诉我"fp32 导出是精确的，问题在量化器"。

最终浏览器加载的是 **CNN 而不是 481MB 的 LoRA 模型**。为什么？三个具体的原因：
481MB 对网页不可接受；int8 量化被 onnxruntime 量化器在 481MB 模型上的 shape-inference
形状冲突卡住（我试了三条路线，报错都记录在 devlog）；fp16 在 CPU/WASM 上**加载即失败**。
这个取舍我写在了 webapp/README 和页面文案里——**页面跑的不是最优模型，这一点不藏**。
浏览器实测：单序列推理 2–15ms，747 条变体的逐碱基敏感度 511–572ms，都远低于 3 秒目标。

## 五、可解释性：为什么我放弃了梯度

论文里的归因通常用 saliency / integrated gradients。但 DNABERT-2 的自定义代码在
`inputs_embeds` 路径上直接报 `TypeError: ones_like(): argument 'input' must be Tensor, not NoneType`
（它硬依赖 input_ids）——梯度根本求不出来。而且它是 BPE 分词，一个 token 跨多个碱基，
梯度映射到碱基还要额外假设。

所以我用了**扰动法**：单碱基饱和突变（每位替换为其余 3 种碱基，747 次前向），
再用 6bp 窗口遮蔽做交叉验证。三个案例里两法一致性 ρ = 0.405 / 0.735 / 0.592。

结果是三个案例里最好看的一个：模型对一条真实 test 序列的高归因位置（126/127/128）
**正落在 JASPAR 数据库里 `pnr`（pannier，GATA 家族）的命中区 123–134 内**，
且命中集合以同源域 + GATA 因子为主——正是果蝇发育增强子的经典组合语法。
量化后：top-10% 高归因碱基落在 motif 区的比例是随机基线的 2.5–2.8 倍。

另一个案例则是彻底的反例：模型预测值最高的那条序列，反而高估了 2.25 个 log2，
而且归因**避开**了所有 motif 命中区（enrichment 0.5，低于随机）。我给它的三个解释是
STARR-seq 的质粒语境差异、模型对 motif 间距/朝向（syntax）不敏感、以及回归长尾的过拟合。

## 六、如果重来一次

1. **先把环境摸清再动模型**。我在 M0–M2 花掉的时间大半与模型无关：TUN 模式和 git 打架、
   Go 程序的 HTTP/2 被代理节点干扰、Zenodo 完全不可达、hf-mirror 间歇性 SSL 断流。
   后来的解决方案都很具体：git 强制 HTTP/1.1、`GODEBUG=http2client=0`、
   用 Clash 的控制器实测节点延迟再切换、大文件一律 `curl -C -` 断点续传 + 重试。
   这些"网络工程"最后成了 devlog 里最长的一节。
2. **风险预判要执行到位**。M5 我预判了 ONNX 的风险，也写了闸门，但 int8 我试了太久——
   第二次失败时就该切方案。
3. **本地绿不等于 CI 绿**。一个 `Path.exists()` 的调用在 Windows 上悄悄返回 False、
   在 Linux 上直接 `File name too long` 崩掉——是 CI 抓到的，而且当时我还误在 CI 失败时
   合并了那个 PR（流程失误也老老实实写进了 devlog）。
